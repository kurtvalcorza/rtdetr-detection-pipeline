## Executive assessment

**Readiness: Needs revision.** The default path works. The pinned snapshot is digest-verified, the carried modules match the generator (`build_notebook.py --check` OK at this SHA), and a Kaggle Tesla T4 record exists for this exact blob. A CPU re-execution in this review reproduced the recorded CPU pre-flight numbers exactly. Five problems stop it from being ready:

1. **The adaptation result has no meaningful reference (RTD-M3).** The baseline is a randomly initialised 3-class head, so its AP is 0 by construction. The synthetic sign task is solved perfectly without learning: a 40-line colour/shape heuristic scores **AP 1.000 / AP50 1.000** on the same 10 held-out images. The adapted model scores AP 0.849 on CPU and 0.916 on T4. The notebook presents 0 → 0.85 as adaptation progress and never says how easy the task is.
2. **Run all needs a manual restart** after the in-kernel pip install. The exact-blob Kaggle record needed one (RTD-M1).
3. **Reruns never reset to the pretrained model, and `FREEZE_BACKBONE` cannot reach the computation on a rerun (RTD-M2).** Setting `FREEZE_BACKBONE = False` and rerunning Section 8 keeps the backbone frozen while the run reports `freeze_backbone: False`. Training continues from the adapted weights (first-epoch loss 15.53 vs 39.62), and Section 9 then shows AP 0.969 against the original 0.000 baseline.
4. **The BYOD dataset branch is a placeholder (RTD-M4).** It contains `byod_records = []`, so `USE_BYOD_DATASET = True` raises `ValueError: dataset must hold at least one record`. There is no loader or upload. The image branch works only with `google.colab`.
5. **The guided layer is missing (RTD-M5).** There is no how-to-use section, roadmap, glossary, prediction, checkpoint, troubleshooting section or conclusion scaffold. The 845-line carried module cell is not labelled or collapsed as infrastructure.

## 3. Findings

### Major

#### RTD-M1 — Run all needs a manual restart after the in-kernel pip install

- **Cell/section:** Section 1 (cell 3); generator `tools/build_notebook.py:69` (stale-import guard) and the install cell it emits.
- **Observed issue:** The cell runs `pip install` for `torch==2.14.0`, `numpy==2.5.3`, `pillow==11.3.0` and other pins into the live kernel. If any already-imported distribution changes, it raises `RuntimeError(... 'Restart the runtime, then rerun from the top.')`. Hosted images preload torch, NumPy and Pillow, so the guard fires.
- **Consequence:** Run all stops at cell 3 on a fresh hosted runtime. The learner must restart and run again, which NOTEBOOK_SPEC says makes a notebook not Run-all conformant. `docs/release-verification.md` calls this "1 automatic restart", but the restart is manual.
- **Evidence:** Documented execution evidence. The Kaggle T4 run of the reviewed blob `315909a9b1a7` records "14/14 ok code cells executed cleanly (1 restart after install cell)". Source inspection of cell 3. Not reproduced locally, because the install was skipped.
- **Recommended correction:** Use the fleet's uv isolated-environment pattern instead of a new install guard. A carrier cell bootstraps uv, creates `uv venv --managed-python --python 3.12.12 <ROOT>/env`, installs a hash-locked `requirements.txt` with `uv pip install --require-hashes --only-binary :all:`, and runs the workload in that environment, so the kernel's preloaded torch and NumPy are never replaced. This repository's own `tutorials/DIMER_MultiModel_Closed_Set_Object_Detection_Workshop.ipynb` already made this move in `46a300c`. The fleet references are `ast-audio-classification-pipeline/tutorials/DIMER_Sound_Event_Classification_Workshop.ipynb` and `bioclip2-biodiversity-pipeline/tutorials/DIMER_Philippine_Biodiversity_Field_Survey_Capstone.ipynb`. Update `docs/release-verification.md` so a restart is never described as automatic.
- **Acceptance check:** A fresh Colab (or Kaggle) runtime completes Run all of the new blob with code-cell execution counts 1..N, no restart and no `RuntimeError` from cell 3, recorded in `docs/release-verification.md` with blob id and runtime.
- **Spec:** RUN10, ENV6, REL11, §25.7.

#### RTD-M2 — Reruns never reset to the pretrained model, and `FREEZE_BACKBONE` cannot reach the computation on a rerun

- **Cell/section:** Sections 7–9 (cells 17, 19, 21); `RTDetrDetectionPipeline.finetune` in `src/rtdetr_detection_pipeline/pipeline.py` (the `freeze_backbone` branch only ever sets `requires_grad = False`); template `tools/notebook_template.py:222–229`.
- **Observed issue:** `finetune` mutates `adapter` in place. Section 8's form fields (`LEARNING_RATE`, `BATCH_SIZE`, `FREEZE_BACKBONE`) invite a change-and-rerun, but rerunning Section 8 continues from the adapted weights. Setting `FREEZE_BACKBONE = False` after a frozen run does not unfreeze anything, because nothing sets `requires_grad = True`. The run dictionary still reports the requested value.
- **Consequence:** A learner who changes one thing and reruns Section 8 and then Section 9 sees a cumulative 6-epoch model compared against the original 0.000 baseline, with provenance that says the backbone was trainable when it was not. The experiment is invalid and its label is wrong.
- **Evidence:** Direct execution (CPU, probe `rerun`). Before the rerun, the backbone was frozen. After the rerun with `FREEZE_BACKBONE = False`, `run['freeze_backbone'] = False` but the backbone is still frozen, and `trainable_parameters` is still 19,259,121. Rerun epoch losses were 15.53 / 13.30 / 11.26, against 39.62 at the start of the first run. Section 9 then printed AP 0.9687 against baseline 0.0000.
- **Recommended correction:** Make Section 8 rebuild the adapter from the verified snapshot (or a cached pre-adaptation state dict) at the start of each run, so every run starts from the pretrained model. In `finetune`, set `requires_grad` explicitly in both directions. Add a one-line rerun instruction to Section 8: "after changing a value, rerun Sections 7–9". Have the comparison table print the epoch count and freeze state that produced each column.
- **Acceptance check:** In one kernel, run the default path, set `FREEZE_BACKBONE = False`, and rerun the documented cells. The first-epoch loss equals that of a fresh run with the same setting (within float tolerance), `trainable_parameters` equals the full count (42,733,137 on this checkpoint), and the reported freeze state matches `requires_grad`.
- **Spec:** SRC2, GDL10, UX7, FT5, FT6.

#### RTD-M3 — The adaptation gain is measured against a baseline that is zero by construction, and the synthetic task is solved by a non-learned heuristic

- **Cell/section:** Sections 6–9 (cells 14–21) and the Interpretation; `sign_dataset` in `samples.py` (fixed 6-slot grid, plain tinted background, fixed sign colours); template `tools/notebook_template.py` Sections 7/9 and the closing cell.
- **Observed issue:** The "pre-adaptation baseline" is the re-headed model with class biases initialised to p = 0.01. It emits 0 detections on all 10 held-out images, so AP = 0.000 by design. The prose says so ("that is the expected starting point"). The task itself is trivially separable: each class has a fixed colour and shape (solid red octagon, red-outlined triangle, red ring), drawn on one of six fixed slots against a plain background.
- **Consequence:** The headline comparison (0.000 → 0.849 on CPU, 0.916 on T4) only shows that a randomly initialised head learns something. It gives the learner no reference for judging whether 0.85 is good. A colour threshold beats the adapted detector, so the learner is likely to conclude that this is what 3-epoch fine-tuning of a 42.7 M-parameter detector buys. The "does not demonstrate" note limits real-world claims but does not mention how easy the task is.
- **Evidence:** Direct execution (CPU, probes `default` and `shortcut`). The heuristic finds a red-pixel blob per generator slot and assigns a class from fill ratio and top-vs-bottom red mass, with no learning. Scored by the notebook's own `average_precision` on the same `held_out` split, it reaches AP 1.000 / AP50 1.000 / AP75 1.000 (all three classes 1.0), and 1.000 on the seed-99 images. Adapted model: AP 0.8494 on CPU (speed-limit AP50 0.646), 0.9161 on the Kaggle T4 record. Caveat: the reviewer wrote the heuristic knowing the generator.
- **Recommended correction:** Add at least one reference that a learner can read the adapted number against. Options: (a) a simple non-learned colour/shape baseline, explained as "what the synthetic task allows without learning"; (b) the frozen COCO model's `stop sign` detections mapped to `stop-sign`, a meaningful zero-training reference for one class; or (c) a harder generator (cluttered or photo backgrounds, colour jitter, occlusion, free placement) where a heuristic fails. Rewrite the Section 9 and Interpretation prose so the gain is attributed to the comparison actually run.
- **Acceptance check:** Section 9 prints at least one non-trivial reference alongside the baseline and adapted columns on the same held-out split. The Interpretation states how the adapted AP compares with it. If option (c) is chosen, the probe's heuristic (`run_probes.py`, `probe_shortcut`) scores AP50 < 0.5 on the new held-out split.
- **Spec:** EVAL10, EVAL15, GDL14, DAT8.
